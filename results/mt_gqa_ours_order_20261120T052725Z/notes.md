## 9. 측정하지 않은 것과 한계

- **본실험은 1회다.** 같은 구성을 본실험 규모로 두 번 돌렸을 때의 TTFT 변동은 재지 않았다(미실행). 참고로 DEV 40장의 gate 단계(`devgate`, 판정에 쓰지 않음)에서
  Ours(원래 순서)를 같은 요청에 두 번 실행한 두 arm의 followup TTFT 평균은 147.47 ms와 146.70 ms(비 0.9948, 각 756건)였다. 즉 완전히 같은 구성끼리도 0.5% 정도의 차이가 났고,
  본실험의 두 방식 차이(비 0.9991)는 그보다 작다. 이 참고값의 두 arm은 자리 교대 없이 항상 같은 순서로 실행되었다.
- **기준 a는 비열등 기준이다.** 정답률 차이의 CI [−0.07, +0.33] pp는 0을 포함한다. "원래 순서가 더 정확하다"는 입증되지 않았고, 확인된 것은 하한이 −0.5 pp보다 크다는 것이다.
  두 방식의 생성 토큰열이 다른 요청은 T2 41건, T3 40건(8,122건 중 81건, 1.0%)이며 나머지는 토큰까지 같다.
- **저장량이 25%를 넘는 구성은 재지 않았다(미실행).** 이 실험에서는 저장한 것을 전부 읽으므로 행 순서가 읽기량에 영향을 주지 않는다(기준 c).
  저장은 더 많이 하고 요청 때 그 일부만 읽는 구성에서는, 재배열 순서는 각 layer 구간의 앞부분만 읽으면 되지만 원래 순서는 그렇게 할 수 없다. 그 경우의 읽기량·TTFT는 이 결과로 알 수 없다.
- **다른 모델·데이터셋·벡터는 재지 않았다(미실행).** LLaVA-NeXT-7B, MT-GQA, PYR-beta-raw, 25% 한 가지다.
- **IMPRESS와의 비교**는 2026-11-17 실행의 저장된 요청별 결과를 쓴 것이다. 정답률 차이는 같은 요청끼리 짝지은 값이지만, TTFT 차이(†)는 서로 다른 날의 실행에서 잰 값의 차이다.
  ReComp·FullLoad·Ours(재배열)의 생성 토큰열이 그 실행과 398장 전체(각 12,183건)에서 같음을 확인한 뒤에 냈다.
- **GPU 적재 시간**(6절)은 적재 호출 구간의 벽시계 시간이며 GPU 커널만의 시간이 아니다. 동기 H2D 복사가 앞선 layer 연산의 완료를 기다리는 시간이 섞여 있어,
  값의 대부분은 대기다. 두 방식에 같은 정의를 썼으므로 비교에는 쓸 수 있지만 "행을 흩어 쓰는 비용" 자체의 크기로 읽으면 안 된다. 그 비용만 따로 재지는 않았다(미실행).
- **T1 저장 비용**(5절)의 두 열은 같은 이미지의 서로 다른 턴 1 요청에서 만든 store의 값이다. "행 골라내기"의 차이(60.4 ms 대 13.4 ms)는 구현 차이에서 나온다:
  재배열은 layer마다 이미지 토큰 전체를 순열로 재배치한 뒤 앞 k_l개를 자르고, 원래 순서는 k_l개만 골라낸다. 파일 쓰기와 fsync는 page cache 상태의 영향을 받는다.
  메타데이터 크기의 차이에는 인덱스 표의 부호화 방식(layer별 목록을 그대로 쓰지 않고 표 두 개로 둠; 계약 12절 5번)이 반영되어 있다.
- **warm cache, 동기 읽기 arm(본실험), O_DIRECT·io_uring, 워커 여러 개, SMART·NAND 수준 측정**은 하지 않았다(미실행).

## 지시와 다르게 했거나 지시에 없던 것 (계약 12절에 실행 전 기록)

- **gate 2의 판정 범위**: 처음 구현은 "질문 3개 → store가 바이트까지 같다"였다. 개발 리허설에서 인덱스 표·행 수·byte table·파일 구성은 같았지만 KV payload 바이트가
  프롬프트 길이가 다른 질문 사이에서 달랐다. 원인(턴 1에서 캡처되는 Visual KV가 프롬프트의 토큰 길이에 따라 달라짐; 현재의 Ours(재배열) store도 같음)을 확인해 사용자에게 알렸고,
  사용자가 "선택·배치 일치로 판정, payload 바이트는 보고"를 선택했다(2026-11-20, 본실험 freeze 전). 이 선택이 없었다면 gate 2는 FAIL이고 본실험은 실행되지 않았다.
- **arm 순서의 자리 교대**: 이전 프로토콜의 순환 회전에 두 Ours의 자리 교대를 더했다(계약 4절). 6절의 직전 arm별 TTFT를 보면 두 방식 모두 FullLoad 직후가 다른 Ours 직후보다 0.5–0.6 ms 느리다.
  자리 교대가 없었다면 이 차이가 Ours(재배열)에만 실렸을 것이다(비율로 약 0.4%, 기준 b의 2%보다 작다).
- **gate 3·5의 DEV 40장 확인**은 별도 phase(3 arm, 3,402건)로 돌렸다. **gate 6의 "모두 통과"**는 이 작업 전부터 환경 문제로 실패하는 테스트(4.57.6에서 3개, 5.13.1에서 2개)를 뺀 뜻으로 읽었다.
- **gate 4의 비교 대상**은 `runs/mt_gqa_impress_code_20261117T185832Z/main`의 요청 단위 원본이다(`results/…`에는 집계만 있다).
