> ## 3. 요청하신 내용 중 고쳐 적은 것

> - **c.** "예산이 0인 첫 layer는 앞 절반을 읽는다"는 맞지만, 공개 코드에서 예산이 0인 경우는 프로세스의 첫 요청뿐이다. 예산 변수를 요청마다 초기화하지 않기 때문이다. 이식본은 공개 코드를 따른다(요청 사이에 이어짐). 앞 절반 규칙이 적용된 요청 수를 보고서에 적는다.
> - **e.** 공개 코드의 정확도 경로는 prefetch된 KV를 채워 넣은 뒤 선택에서 빠진 토큰을 mask로 가린다. 즉 "모두 채워 넣고 그대로 쓰는" 것은 성능 측정 경로에만 해당한다.
> - 그 밖의 a, b, d, f, g, h, i, j는 읽은 내용과 일치한다.

> ## 4. 공개 코드를 직접 호출해 대조하는 범위 (gate 1)

> - 직접 호출: `PrefixKVLayer.prefetch_by_chunk`의 순서 변환, chunk 번호 계산, 예산 자르기, 앞 절반 규칙, prefetch된 토큰 집합(P 1665–1715). 객체를 디스크 없이 만들고 읽기 함수만 기록용으로 바꿔 같은 입력에서 같은 chunk 목록과 토큰 집합이 나오는지 본다.
> - 직접 호출하기 어려운 부분: 예측 집합(`sele_tokenids.clone()`)과 빠진 토큰 계산(`~torch.isin`)은 F의 1,300줄짜리 layer 함수 안에 있어 모델 가중치와 전역 상태 없이는 부를 수 없다. 그 두 줄과 같은 연산을 테스트 안에 적고 같은 입력에서 이식본의 결과와 비교한다. 이 사실을 테스트와 보고서에 적는다.

## 11. 코드, 지시와 다르게 한 것, 한계

### 추가한 코드 (기존 파일은 수정하지 않았다)

- `mmimpress/hyperinfer.py`: HyperInfer. IMPRESS 선택기를 상속하고 store 읽기 지점만 prefetch buffer를 거치게 한다. 순수 함수(위치 표, 예측 chunk, 예산 자르기), worker 작업, 디버그용 NaN 검사 래퍼, 요청 함수.
- `tests/test_hyperinfer.py`: 15개 테스트. 공개 코드 `prefetch_by_chunk` 직접 호출 대조, prefetch 끔 ≡ IMPRESS, prefetch 켬에서 선택·mask·cache 내용이 IMPRESS와 같음, 바이트·chunk 회계, 예산 상태의 요청 간 이어짐, NaN 검사 래퍼.
- `scripts/225_eval_mt_gqa_hyperinfer.py`: 실행(상수 측정, freeze, gate·dev·main 단계). 두 모델의 기존 본실험 하네스(`scripts/222`, `scripts/206`)를 import해 그대로 쓴다.
- `scripts/226_validate_mt_gqa_hyperinfer.py`: gate 판정.
- `scripts/227_report_mt_gqa_hyperinfer.py`: 이 보고서.
- `scripts/run_mt_gqa_hyperinfer.sh`: 드라이버.
- 문서: `docs/hyperinfer_port_contract.md`(원본 대조표), `docs/mt_gqa_hyperinfer_contract.md`(실행 계약), `docs/mt_gqa_hyperinfer_chunk_times.json`(동결한 상수).

### 측정하지 않은 것과 한계

- ReComp, FullLoad, IMPRESS, Ours는 다시 돌리지 않았다. 표의 값은 기존 본실험의 것이고, HyperInfer와의 TTFT 차이는 서로 다른 실행 사이의 차이다. 같은 실행에서 함께 잰 값은 DEV 40장의 FullLoad, IMPRESS, HyperInfer뿐이다.
- 캐시 계층(GPU·CPU 캐시, CKLFU), 주기적 재배치, warm-up은 이식하지 않았다. 모든 요청이 cold SSD다.
- chunk 읽기 시간 상수는 GPU가 쉬는 상태에서 잰 평균이다. 요청 중에는 GPU 계산과 Python 실행이 겹치므로 worker의 실제 읽기 시간은 다를 수 있다. 차이는 prefetch 대기 시간으로 드러난다.
- 기존 IMPRESS 행에는 GPU 적재 시간과 선택 계산 시간이 따로 없어 8절에서 HyperInfer와 나란히 놓지 못했다.
- Oracle, History 방식(논문 VI-D의 비교 대상)은 만들지 않았다.
- SSD 쓰기량은 장치 전체의 커널 카운터다(이 실행 외의 쓰기 포함, NAND 쓰기량 아님). SMART 값은 root 권한이 없어 읽지 못했다.

### 지시와 다르게 했거나 지시에 없던 것

계약 9절의 10개 항목이 전부다(`docs/mt_gqa_hyperinfer_contract.md`). 요약:

1. **gate 실패 시 동작.** 한 모델의 gate가 실패하면 그 모델의 본실험만 건너뛰고 다른 모델은 그대로 진행한다. 지시는 "그 모델의 본실험을 시작하지 않고 … 종료한다"인데, 무인 실행에서 나머지 모델까지 버리지 않도록 이렇게 해석했다. gate 7이나 gate 1(두 모델 공통)이 실패하면 어느 모델도 측정하지 않고 종료한다.
2. **DEV 단계 하나.** DEV 40장을 7개 arm으로 한 번만 돈다(gate 2–6과 gate 8을 같은 실행에서 본다). SSD 쓰기량과 시간을 줄이기 위해서다. gate 8의 FullLoad·IMPRESS TTFT는 7개 arm 회전 속에서 잰 값이다.
3. **gate 5의 방법.** 6절 5번에 적은 대로 mask된 열에만 0을 넘긴다.
4. **예산의 범위.** 대조표 c의 정정대로 공개 코드를 따른다. arm마다 따로 두는 것은 gate용 arm이 본 arm의 예산에 영향을 주지 않게 하기 위해서다.
5. **계산 시간의 측정.** 공개 코드는 CUDA event로 재지만 여기서는 HuggingFace 모델의 forward 안에서 돌기 때문에, 제출 시각부터 다음 layer 시작의 GPU 동기화까지를 잰다. prefetch를 켠 arm은 layer마다 GPU 동기화가 한 번 더 들어간다(끈 arm에는 없다).
6. **worker의 읽기 단위.** worker는 chunk 하나에 pread 한 번씩 읽는다(공개 코드의 chunk별 반복과 같다). 동기 복구 읽기는 IMPRESS 이식본처럼 인접 chunk를 합친다. 상수는 worker의 읽기 방식 그대로 잰 값이다.
7. **IMPRESS arm의 사용 집합 기록.** gate 2, 3에서 layer별 사용 집합을 비교하려면 IMPRESS arm의 선택 결과가 필요하다. 기존 하네스는 이를 행에 남기지 않으므로, IMPRESS 요청 함수 바깥에 통과만 시키는 기록기를 두고 요청이 끝난 뒤 요약값(layer별 SHA256 앞 12자)을 행에 적는다. IMPRESS의 코드 경로는 바뀌지 않는다.
8. **상수 측정 조건.** GPU 계산과 동시에 읽는 실제 상황이 아니라 GPU가 쉬는 상태에서 잰다. 모든 chunk 위치의 평균이라 layer의 첫 chunk만 보면 이보다 느릴 수 있다. 위치별 값은 측정 파일에 있다.
9. **probe 읽기 시간.** 예산에서 빼지 않는다(3절). 넘친 시간은 대기로 드러나고 그대로 보고한다.
10. **하네스 재사용 방식.** 두 모델의 기존 본실험 스크립트를 import해서 이미지 단위 실행·이어서 실행·커밋 코드를 그대로 쓰고, 이 실행의 프로세스 안에서만 arm 표, 단계 표, 요청 분기, 이미지 감사, 상태 기록기를 바꿔 끼운다. 기존 스크립트 파일은 수정하지 않는다.
